## 1. 测试与边界

### 1.1 分析基线

```text

clock:             1 周期 = 2 ns
```

### 1.2 负载结构

fireye/B2 是 RMQ（区间最值）预处理 + 二分查询算法：

```text
main:
    init(dl, L, 100, max)    # 构建 max 稀疏表 dl[20][100]（8KB）
    init(dr, R, 100, min)    # 构建 min 稀疏表 dr[20][100]（8KB）
    LOOP=2 次：
        for i in 1..100:
            while (l <= r):   # 二分
                mid = ...
                query(dr,...) - query(dl,...) + 1 >= mid ?
                ...
    printf("%d\n", ans)
```

每轮 init 由多个双 load 内循环构成：

```text
init 内循环（dl，max）:
    add.w@b0 + ld.w@b4      (配对)     ← ld.w 读 d[i-1][j]
    ld.w@b8 + addi.w@bc     (配对)     ← 第二个 ld.w 读 d[i-1][j+t]（双 load）
    bge@c0                  (单独)     ← 比较两 load 结果 → gap=2（load-use）
    st.w@c8 + addi.w@cc     (配对)
    bne@d0                  (单独)     ← 循环回跳 → gap=6（分支恢复）
```

**注意**：`dl` 和 `dr` 各 8KB，合计 16KB，而 D-Cache 仅 8KB 且为 2 路——两个稀疏表会互相驱逐（容量压力）。

### 1.3 计时区间

B2 无显式计时器。分析采用 **main 区间**：

```text
main 起点: [0000017652ns] pc = 1c000800
main 终点: [0000159298ns] pc = 1c000b68（main 返回）
周期 C    = (159298 - 17652) / 2 + 1 = 70824
```

## 4. 双发重建（RTL 规则贪心）

配对率与双提交数据接近（51.4%），主要单发原因与 A0 相同为结构冲突与真 RAW，但 B2 的指令流更碎（小循环 + 调用），配对机会天然偏少。

## 5. 提交空拍归因（核心）

### 5.1 gap 直方图

| gap | 次数 | 空拍合计 | 归因 |
| --- | ---: | ---: | ---: |
| 1 | 22853 | 0 | 连续提交 |
| 2 | 7202 | 7202（10.2%） | load-use 单拍空泡 |
| 3–5 | 6 | ~0 | — |
| **6–10** | 2952 | **19596（27.7%）** | **分支恢复（最大瓶颈）** |
| 11–20 | 248 | 3312（4.7%） | 长停顿 |
| 21–40 | 74 | 2201（3.1%） | 长停顿 |
| 41–80 | 77 | 4062（5.7%） | 长停顿 |
| >80 | 10 | 517（0.7%） | 退出/异常 |

### 5.2 归因 1：分支恢复（27.7%，最大瓶颈）

`gap 6–10` 共 2952 次，其中 **2861 次（96.9%）前一提交组含 branch**，空拍合计 19596 拍（27.7% of C）。

来源：

- init 双 load 循环的 `bne@d0` 回跳（每迭代 1 次）；
- query/log_2 小循环的 `beq@90`、`bne@38`、`bne@78` 回跳；
- 这些是**规律循环回跳**，本应高度可预测，却每次恢复 6 拍。

**B2 的循环体很小（3~5 条指令），分支恢复代价占比极高**。若每次迭代都误预测，循环效率极低。建议重点调查 BTB/PHT 对小循环回跳的预测行为。

### 5.3 归因 2：load-use 单拍空泡（10.2%）

`gap=2` 共 7202 拍，其中 3785 拍（52.6%）前组含 load。典型模式：

```text
init 循环:  ld.w@b4 / ld.w@b8 → bge@c0（比较双 load 结果）
```

两个 load 结果都要等待，`bge@c0` 必须等最晚的 load。与 A0 相同的根因：`EXE_forward_ok` 不覆盖 load。

### 5.4 归因 3：长停顿（gap>10，约 10.9%）

`gap 11–80` 合计约 10092 拍（14.2%），其中 379 次无法归因、20 次为 `bl` 调用（printf）、10 次前组含 load。结合 `dl/dr` 合计 16KB > 8KB D-Cache 的容量压力，部分长停顿来自 D-Cache miss 与 clean eviction 写回。**B2 的访存规模恰好是 A0 与 CoreMark 的中间态**，D-Cache miss 不是主瓶颈但存在。

## 6. 反事实分析

| 优化 | 候选空拍 | 相对总周期上限 |
| --- | ---: | ---: |
| 完美分支预测（消除 6~10 拍 gap） | ~19596 | **27.7%** |
| load-use 消除 | ~7202 | 10.2% |
| 长停顿消除（D-Cache/bl/退出） | ~10092 | 14.2%（含 printf 调用，部分不可优化） |

**B2 的第一瓶颈是分支恢复（27.7%），与 A0（load-use 25.1%）、CoreMark（结构冲突 41.2%）完全不同。**

## 7. 跨负载总结（fireye 系列 + CoreMark）

| 维度 | CoreMark | fireye/A0 | fireye/B2 |
| --- | ---: | ---: | ---: |
| 负载类型 | 混合 | 顺序大数组 | 控制流密集（小循环+二分） |
| IPC | 0.987 | 1.015 | 0.635 |
| 配对率 | 53.1% | 97.3% | ~51% |
| 第一瓶颈 | 结构冲突 41.2% | load-use 25.1% | **分支恢复 27.7%** |
| 第二瓶颈 | 分支恢复 11.0% | D-Cache miss 12.7% | load-use 10.2% |

**关键结论（印证手册 14.2）：**

1. **没有任何单一优化对全部负载有效**：CoreMark 需要副槽能力，A0 需要 load-use 前递，B2 需要分支预测改进——三者瓶颈完全不同。
2. **分支恢复是所有负载的共同问题**：CoreMark 11.0%、A0 10.0%、B2 27.7%。循环回跳分支（bne/bge/beq）在三个负载中都频繁触发恢复，说明 BTB/PHT 对规律循环分支的预测率存在系统性短板。
3. **load-use 也是共同问题**：CoreMark 部分、A0 25.1%、B2 10.2%。
4. **副槽类优化（BRU/双访存）只对 CoreMark 有效**：fireye 系列配对已饱和或结构天然单发，副槽优化收益 ≤1.2%。

## 8. 结论摘要

```text
整体 IPC 的第一瓶颈：    52.8% 空拍；分支恢复 27.7% + load-use 10.2% + 长停顿 14.2%
双发配对的第一瓶颈：     无显著结构瓶颈（51.4% 配对率，控制流密集天然单发多）
最不值得优先做的优化：   副槽 BRU / 双访存（fireye 系列收益 ≤1.2%，仅 CoreMark 有效）
最有价值的优化方向：     分支预测改进（27.7%，且是跨负载共同短板）
数据可信度：             main 区间统计；守恒校验通过（37401==37401）；
                         无显式计时器；printf 占 13.9% 需注意；归因为启发式
```

## 9. 局限与下一步验证

### 9.1 局限

- 无显式计时器，周期为时间戳换算；
- printf 相关函数占 main 区间 13.9%，对 IPC 有稀释（main 纯计算 IPC 会更高）；
- 单次配置（LOOP=2），循环预热有限；
- 归因为提交间隔启发式。

### 9.2 建议计数器

```text
branch_mispredict（按分支 PC 分类）  确认 27.7% 分支恢复；定位 bne@d0/beq@90 等
                                     循环回跳为何高误预测率（BTB 别名 / PHT 饱和 / 初始化污染）
load_use_wait                       确认 10.2% load-use（双 load → bge 链）
dcache_miss                         确认 dl/dr 16KB 容量 miss 与 clean eviction 写回
```

### 9.3 对优化文档的补充意见

优化文档未将"分支预测改进"列为优先项，但**本分析显示分支恢复是 fireye/B2 的第一瓶颈（27.7%），且是三个负载的共同短板（11%/10%/27.7%）**。建议补充：

1. 优先调查**循环回跳分支**的误预测原因：BTB 只有 8 位 tag（`PC[19:12]`），小循环内多个分支共享索引时可能互相污染；PHT 为 2-bit 饱和计数器，规律循环理论上应稳定命中——若实测仍高误预测，需检查更新时机（`inst_br` 与 `actual_taken` 的 MEM 级更新是否被 flush 干扰）；
2. 考虑**小循环优化**（B2 循环体仅 3~5 条指令，一次误预测损失 6 拍 ≈ 循环体 2 倍长度）；
3. 分支恢复路径缩短（EXE 直接重定向）对 B2 收益最高，但时序风险大，需权衡。
