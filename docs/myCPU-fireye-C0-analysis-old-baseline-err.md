### 1.1 分析基线

```text

```

### 1.2 负载结构

fireye/C0 是 **Trie 构建 + DFS 深度优先搜索**（双 Trie 同步匹配计数）：

```text
main:
    run():
        insert(t[0], C0_data0[i])  × 50     # 构建 Trie 0
        insert(t[1], C0_data1[i])  × 50     # 构建 Trie 1
        LOOP=2 次: ans=0; dfs(1,1)
    printf("%d\n", ans)

dfs(x, y):                            # 递归深度 4（C0_n=C0_m=2）
    if x==3: ++ans; return
    for i in 0..25:                   # 26 路循环
        nx = t[0].ch[lastN][i]; ny = t[1].ch[lastM][i]
        if (nx && ny):
            mpN[x][y]=nx; mpM[x][y]=ny
            dfs(下一格)
```

**数据规模**：两个 Trie `t[0].ch[100][26]` + `t[1].ch[100][26]`，每个 10.4KB，合计 20.8KB；另有 `mpN[6][6]`/`mpM[6][6]`。**合计远超 8KB D-Cache，且 DFS 对 Trie 的访问为随机模式**（按字符分支跳转），预取无效。

### 1.3 计时区间

C0 无显式计时器。采用 main 区间：

```text
main 起点: [0000076144ns] pc = 1c000800
main 终点: [0000531450ns] pc = 1c00085c（main 返回）
周期 C    = (531450 - 76144) / 2 + 1 = 227654
```

## 4. 双发重建（RTL 规则贪心）

双提交 55.4% 与配对率相当。dfs 指令流含大量 load/mul/分支，normal 指令多为索引计算链（`mul.w` 后紧跟 `add.w`），RAW 相关频繁，配对机会受限。mul 占比 5.45% 且有 1 拍等待，是系列特有现象。

## 5. 提交空拍归因（核心）

### 5.1 gap 直方图

| gap | 次数 | 空拍合计 | 归因 |
| --- | ---: | ---: | ---: |
| 1 | 115758 | 0 | 连续提交 |
| 2 | 25850 | 25850（11.4%） | load-use / mul 等待 |
| 3–5 | 1552 | 4660（2.0%） | load/mul 延迟 |
| **6–10** | 5069 | **32324（14.2%）** | **分支恢复** |
| 11–20 | 266 | 3861（1.7%） | D-Cache miss |
| 21–40 | 195 | 5773（2.5%） | D-Cache miss |
| 41–80 | 146 | 8761（3.8%） | D-Cache miss |
| >80 | 8 | 580（0.3%） | 异常/退出 |

### 5.2 归因 1：分支恢复（14.2%）

`gap 6–10` 共 5069 次，其中 5046 次（99.5%）前组含 branch，空拍 32324 拍。

来源：dfs 的 `beq@34`、`beq@54`（Trie 子节点判空）、`bge@64`（行末检查）、`beq@90`（递归返回后的 26 路循环条件），以及递归调用的返回。**递归搜索的分支模式难以预测**（节点存在性依赖数据），误预测率高是结构性的。

### 5.3 归因 2：load-use 与 mul 等待（13.4%）

`gap=2` 共 25850 拍：

```text
load-use:   13162 次（前组含 load）—— ld.w@30→beq@34、ld.w@50→beq@54 等
mul 等待:    1607 次（前组最后为 mul.w）
其他:       11081 次（多为 load→mul 链：ld.w@f8→mul.w@04，前组 load 但下一条是 mul）
```

`gap 3–5` 共 1552 次全部前组含 load（或 mul 后的长链）。

**C0 的 load→mul 索引链**（`ld.w@f8 → mul.w@04`）使 load 与 mul 延迟叠加，单次停顿可达 2~3 拍，是 A0/B2 没有的现象。

### 5.4 归因 3：D-Cache miss（约 8.3%）

`gap>10` 合计 17409 拍（7.6%），前组最后 PC 集中在 `beq@90`、`add.w@4c`、`add.w@2c`、`add.w@00`——都是 **dfs 内紧跟 load 之后的分支/计算**，即下一个 load 访问 Trie 节点未命中。

根因：

- Trie 表 20.8KB >> 8KB D-Cache；
- DFS 按数据驱动的字符分支**随机跳跃访问**，无顺序局部性，`dbuffer` 预取完全无效；
- 每次 miss 触发 16-beat AXI refill（约 30~40 拍，从 gap 41~80 可见）。

**这是 C0 最独特的瓶颈：缓存容量 + 随机访问模式的组合，与 A0（顺序流）、B2（稀疏表互相驱逐）都不同。**

### 5.5 递归调用开销

含 `bl` 的提交组 495 次（dfs 递归 + 少量 printf）。dfs 每次递归进出需要保存/恢复 9 个寄存器（`st.w/ld.w` × 9，见反汇编 0x878~0x8c0），递归框架开销不可忽略，但相对 dfs 主循环占比小。

## 6. 反事实分析

| 优化 | 候选空拍 | 相对总周期上限 |
| --- | ---: | ---: |
| 完美分支预测（6~10 拍 gap） | ~32324 | **14.2%** |
| load-use + mul 延迟消除（gap 2~5） | ~30510 | 13.4% |
| D-Cache miss 消除（gap>10） | ~17409 | 7.6%（含部分不可优化） |

**C0 的瓶颈结构：分支恢复（14.2%）与 load/mul 延迟（13.4%）并重，D-Cache miss（7.6%）为第三。** 与 A0（load-use 25%）、B2（分支 27.7%）不同，C0 的延迟来源更分散。

## 7. 跨负载总结（五个 benchmark 对齐）

| 维度 | CoreMark | A0 | B2 | **C0** |
| --- | ---: | ---: | ---: | ---: |
| 负载类型 | 混合 | 顺序大数组 | 控制流密集 | **递归+随机访存+mul** |
| IPC | 0.987 | 1.015 | 0.635 | **0.905** |
| 第一瓶颈 | 结构冲突 41.2% | load-use 25.1% | 分支恢复 27.7% | **分支恢复 14.2%** |
| 第二瓶颈 | 分支恢复 11.0% | D-Cache miss 12.7% | load-use 10.2% | **load/mul 延迟 13.4%** |
| 第三瓶颈 | 单拍气泡 13.7% | 分支恢复 10.0% | 长停顿 14.2% | **D-Cache miss 7.6%** |

**关键结论（进一步印证手册 14.2）：**

1. **分支恢复是 3/4 负载的第一或第二瓶颈**（CoreMark 11%、A0 10%、B2 27.7%、C0 14.2%）——跨负载共性最强，最值得系统性改进；
2. **load-use / 访存延迟是另一共性**（A0 25%、B2 10%、C0 13%、CoreMark 部分）——`EXE_forward_ok` 不覆盖 load 是所有负载的共同痛点；
3. **D-Cache miss 的形态随负载变化**：A0 顺序流（dbuffer 可部分缓解）、B2 容量驱逐、C0 随机访问（预取无效）——需要不同对策；
4. **副槽类优化只在 CoreMark 有效**（fireye 系列收益 ≤1.2%）。

## 8. 结论摘要

```text
整体 IPC 的第一瓶颈：    34.6% 空拍；分支恢复 14.2% + load/mul 延迟 13.4%
                        + D-Cache miss 7.6%
双发配对的第一瓶颈：     dfs 指令链 RAW 相关频繁（load→mul→add 链），配对率 ~55%
最不值得优先做的优化：   副槽 BRU / 双访存（fireye 系列收益 ≤1.2%）
最有价值的优化方向：     分支预测改进（跨负载共同短板）；load-use/mul 延迟；
                        C0 特有：大稀疏表随机访问的 cache 对策
数据可信度：             main 区间统计；守恒校验通过（78809==78809）；
                         无显式计时器；dfs 占 92.5% 无污染；归因为启发式
```

## 9. 局限与下一步验证

### 9.1 局限

- 无显式计时器，周期为时间戳换算；
- 单次配置（LOOP=2），DFS 分支模式可能随数据变化；
- 归因为提交间隔启发式，`load→mul` 链的精确停顿级数需周期级确认。

### 9.2 建议计数器

```text
branch_mispredict（按 PC）     确认 14.2% 分支恢复；区分 beq@34/54（节点判空）
                               与 beq@90（循环条件）的误预测率
load_use_wait                  确认 13.4% load-use（ld.w→beq 链）
mul_wait                       确认 mul 1 拍等待（ld.w→mul.w 链的叠加）
dcache_miss（按访问模式）       确认 7.6% 长停顿；区分 Trie 随机 miss 与顺序 miss
icache_miss                    检查 dfs 递归是否导致取指 miss
```

### 9.3 对优化文档的补充意见

1. **load→mul 链是新的瓶颈形态**：优化文档未提及。C0 的 `ld.w@f8→mul.w@04` 链使 load 延迟与 mul 延迟叠加。若实现"乘法固定流水化"（文档 2.5），需同时考虑其与 load-use 的级联；
2. **大稀疏表随机访问的 cache 对策**：C0 的 Trie（20.8KB）随机访问，dbuffer 顺序预取无效。可以考虑：更大 D-Cache（FPGA BRAM 足够）、对 DFS 型负载用软件阻塞缓存（但需改软件）、或接受 miss 并侧重缩短 refill 路径；
3. **分支预测优先级提高**：四个负载中三个分支恢复占比显著，建议作为跨负载优化第一优先项（与优化文档未列此项形成对比）。
